## Rating weighting

Raw `(rating, rating_count)` pairs are converted to a **zero-anchored Bayesian weighted score**:

```
weighted_score = (R × v) / (v + C)
```

- `R` = raw rating value (0–100)
- `v` = rating vote count
- `C` = confidence constant (default = 5)

When `v = 0` the formula collapses to `0`. The score is then normalised to `[0, 1]` by dividing by 100.

## Label weighting

`album_labels_matrix` encodes **which record label(s) released the album**. The source `album_label` parquet has one row per (album, label, tag) triple, so a label appears once per associated tag. Labels are deduplicated to one (album, label) pair and weighted equally:

```python
label_filtered = label_filtered.drop_duplicates(subset=['album_id', 'label_id'])
label_totals = label_filtered.groupby('album_id')['label_id'].transform('count')
label_weight = 1.0 / label_totals
```

This replaced an earlier scheme that weighted by `tag_count`, which systematically underweighted boutique labels carrying few tags against large, heavily-tagged labels. The label *tags* themselves are not used here — they feed only the genre matrix (below).

## Genre tag matrix (`album_genre_matrix.npz`)

Built by `3-features/02-feature-genre.ipynb`. Combines three tag sources into a single matrix using a **three-tier
strategy**. Tags appearing fewer than 10 times across all three sources combined are dropped; rows
are L1-normalised after combining so each album's profile sums to 1.0.

| Tier | Source | Weight | Condition |
|------|--------|--------|-----------|
| 1 | Album tags (direct MusicBrainz tags) | 1.0 | All albums |
| 2 | Artist tags (via primary artist) | 0.5 | All albums |
| 3a | Label tags — **reinforcement** | 0.3 | Masked to tags the album or artist already has |
| 3b | Label tags — **rescue** | 0.3 | Allowlist labels only, and only for albums with no other signal |

**Universal artist tags (tier 2).** Artist tags are blended for *all* albums, not just sparsely
tagged ones. The earlier `< 5 direct tags` threshold was dropped: applying artist tags everywhere
adds **richness** to already-covered albums (sharper similarity) even though it adds no new
**coverage** (a well-tagged album already had signal). See `2-eda/05-EDA-tags-labels.ipynb` for the
coverage-vs-richness analysis.

**Label tag masking (tier 3a).** Applied unconditionally, label tags are mostly noise: a large,
genre-diverse label (e.g. a major) carries tags from across its whole catalogue that don't describe
any one album. ~87% of raw label-tag entries fail to match the album's own album/artist signal and
are masked out. The survivors only *reinforce* genre tags the album already has — a label "jazz" tag
boosts an album already tagged jazz, but the label's "pop"/"rock" tags are zeroed for that album.

**Label allowlist rescue (tier 3b).** For albums with zero album and artist signal, allowlist labels
may *introduce* genre tags as a last resort. A label joins the allowlist if **≥60% of its albums
share at least one tag with the label** (its per-album overlap rate) — a direct measure of genre
coherence. Label size and `label_type` proved to be poor proxies (coherence is bimodal at every
size), so the overlap rate is used instead. The allowlist is computed once at build time.

When a tag ID appears in more than one source for the same album, all sources write to the **same column** and their weighted contributions sum — overlapping tags reinforce rather than duplicate.

Result: 10,255 tag columns vs 2,684 in the album-only matrix (~5.45M non-zero entries), covering
**1,210,648 albums (68.8%)**. This is close to the tag-signal ceiling — the remaining ~31% have no
album tags, an untagged artist, and no allowlist label, so no honest tag-based signal exists for
them. Lowering the 60% allowlist threshold would add coverage only by reintroducing label noise.

## Artist country matrix (`album_country_matrix.npz`)

Built by `3-features/05-feature-country.ipynb` from `sql_feature_artist_country_fast.parquet`. One-hot encoded per album using `country_id_imputed` from the artist country pipeline. 2,014 country columns.

The artist country parquet is produced by `1-data/03-feature-country-import.ipynb`, which runs `1-data/queries/mb_artist_country_fast_duckdb_release.sql`. The query snapshots ~15 Postgres tables into DuckDB once, then resolves each artist's country via 10 signals in priority order:

1. `artist.area` — direct area column (ground truth)
2. `artist.begin_area` — area where artist was formed/born
3. `artist_release` materialised table — modal country across all releases
4. `artist_release_group` materialised table — first/modal country across all release groups
5. `l_area_artist` AR link — area explicitly linked to the artist
6. `l_artist_label` AR link — label's area
7. `l_artist_place` AR link — place's area
8. Release country (local join) — modal country from release events
9. Release group first country — earliest release event country
10. Release group modal country — most common release event country

Areas that are not countries themselves are walked up the MusicBrainz area containment hierarchy (up to 3 levels) via the `l_area_area` "part of" relationship to find their parent country. 62% of artists have no direct area set; of those, ~30% are recovered via imputation, giving `country_id_imputed` for the majority.

**Why country is downweighted to 0.2:** at weight 1.0, the country one-hot block dominated cosine similarity. A single dense binary column (every album has exactly one country) competes against thousands of sparse tag columns where most albums have very few non-zero entries — country's signal dwarfs everything else. The 0.1–0.5 range is the sensible tuning window.

## Track stats matrix (`album_track_stats_matrix.npz`)

Built by `3-features/06-feature-track-stats.ipynb` from `sql_feature_album_track_stats.parquet`. 12 columns per album:

`first_release_year`, `medium_count`, `track_count`, `total_length_ms`, `mean_length_ms`, `median_length_ms`, `stddev_length_ms`, `min_length_ms`, `max_length_ms`, `p25_length_ms`, `p75_length_ms`, `iqr_length_ms`

See `2-eda/06-EDA-track-stats.ipynb` for full distribution analysis, outlier regimes (short interludes, long ambient releases), year imputation coverage, and Spearman correlation heatmap confirming which columns are redundant.

Four columns from the raw parquet are **excluded**: `pct_tracks_with_length` and `track_count_with_length` (data-quality flags, not musical features), and `variance_length_ms` and `range_length_ms` (redundant — `stddev` and `iqr` already capture spread). Each retained column is min-max scaled to [0, 1]; nulls are filled with column medians before scaling.

The track stats parquet is produced by `1-data/04-feature-track-stats-import.ipynb`, which runs `1-data/queries/mb_album_stats_duckdb.sql`. That query has 4 stages:

1. **Snapshot** — filters Postgres down to album-type release groups and materialises them in DuckDB
2. **Canonical release** — picks one release per release group (earliest date, then lowest ID) to avoid inflating track counts across reissues and deluxe editions
3. **Track-length percentiles** — computes p25/median/p75 using `PERCENTILE_CONT`
4. **Join and export** — assembles the final `album_stats` table and exports to parquet

## Feature assembly per model version

### v1
```python
X_final = hstack([X_tags, X_labels, X_types, X_ratings])
```

### v2
```python
X_final = hstack([
    X_tags * 1.0, X_labels * 1.0, X_types * 1.0, X_ratings * 1.0,
    X_country * 0.2, X_track_stats * 1.0
])
```

### v3
```python
X_final = hstack([
    X_genre * 1.0, X_record_label * 1.0, X_ratings * 1.0,
    X_country * 0.2, X_track_stats * 1.0
])
```

v3 swaps the album-only tags for the combined genre matrix and consolidates the separate label + type blocks into `album_record_label_matrix`.

Country is downweighted to 0.2 because at w=1.0 it dominates cosine similarity — it is a dense single-column signal competing against thousands of sparse tag columns.

## Temporal matrix (`album_temporal_matrix.npz`)

Built by `3-features/14-feature-temporal.ipynb`. A 13-column merged block that combines two sub-signals behind the single **Era dial** in the app:

| Columns | Sub-signal | Source | Weight |
|---------|------------|--------|--------|
| 0–9 | Era one-hot (10 bins) | `album_era_matrix.npz` | 1.0 |
| 10 | Continuous year, scaled [0, 1] | `album_era.parquet → best_year` | 0.3 (analytically determined — see below) |

Both sub-signals use the same `best_year` value from the era fallback chain, so they are internally consistent. Unknown albums (no year in any source, ~2.1% of the universe) get zero in all 11 columns.

**Era bins (columns 0–9):**

| Bin | Years | Notes |
|-----|-------|-------|
| `Pre-1900` | before 1900 | 50-yr bucket |
| `1900–1949` | 1900–1949 | 50-yr bucket — sparse pre-modern data |
| `1950s`–`2020s` | decade bins | standard 10-yr buckets |

The era one-hot sub-signal provides coarse decade-level matching. The continuous year column's role is more limited: because the data spans ~975–2026 (1051 years, due to classical/early music), a single decade is less than 1% of the [0,1] range — intra-decade cosine differentiation is negligible regardless of weight. The year column's real effect is **era-boundary smoothing**: albums just either side of a decade boundary (e.g. Dec 1969 / Jan 1970) get a small non-zero similarity that the era one-hot alone cannot provide. `YEAR_WEIGHT=0.3` was chosen analytically to keep this nudge conservative (~0.10 temporal cosine for boundary pairs, ~0.04 contribution to full cosine at Era dial=4). Formal tuning via `4-model/tuning/05-tune-temporal-ratio.ipynb` is blocked — `lastfm_album_similarity.parquet` does not exist. See `2-eda/04-EDA-year.ipynb` for the full analysis.

The intermediate per-album parquet (`data/features/album_era.parquet`) retains `best_year`, `best_year_source`, and `era_bin` for audit and future use. Scaler parameters are saved in `data/features/temporal_year_scaler.json`.

**Source era matrix** (`album_era_matrix.npz`) is built by `3-features/14-feature-temporal.ipynb` (formerly `07-feature-era.ipynb`) using a three-source fallback chain:

1. `release_group_meta.first_release_date_year` (canonical MusicBrainz first-release year)
2. `release_country.date_year` (earliest country-specific date)
3. `artist.begin_date_year` (band formation / artist birth year — noisiest)

Five confirmed data-entry errors patched; years > 2026 hard-capped to Unknown. The era matrix itself is no longer loaded by the app — only the merged temporal matrix is.

## Last.fm popularity matrix (`album_lastfm_popularity_matrix.npz`)

Built by `3-features/13-feature-lastfm-popularity.ipynb` from `data/lastfm_data.parquet` (produced by `1-data/05-lastfm-scraper.ipynb`).

**Pipeline:**

1. Load and clean `lastfm_data.parquet` — strip comma formatting from numeric strings, coerce `N/A` → 0
2. Normalise artist/album names (lowercase + strip non-alphanumeric) and deduplicate, keeping the highest-scrobbles row per (artist, album) pair
3. Join against `mb_album_artists.parquet` on normalised names to obtain `album_id`
4. Min-max scale four numeric features to [0, 1] independently
5. Build a CSR sparse matrix aligned to the master `album_ids.pkl` index; unmatched albums get zero rows

**Output columns (4):**

| Column | Feature |
|--------|---------|
| 0 | `album_listeners` (scaled) |
| 1 | `album_scrobbles` (scaled) |
| 2 | `artist_listeners` (scaled) |
| 3 | `artist_scrobbles` (scaled) |

**Coverage:** ~56% of albums matched (~985k non-zero rows out of 1,758,488). The remaining 44% have zero rows — they contribute no popularity signal to cosine distance and are passively ignored. The match gap is largely due to name normalisation mismatches between Last.fm and MusicBrainz (non-ASCII characters, "The X" vs "X" variants, subtitle differences).

In the weighted app the popularity block participates in the same weighted cosine formula as all other blocks. The **ratings weight auto-syncs to the popularity dial** — turning up Popularity boosts both Last.fm signal and community ratings together, treating them as complementary engagement measures. If the popularity `.npz` is missing the app falls back to a fixed ratings weight (dial 6 ≈ 1.09).

## Column pruning

Applied in all model training notebooks. Columns below `safe_threshold` nnz are dropped, where the threshold is the minimum "best column nnz" across all albums that have any features:

```python
safe_threshold = int(max_col_nnz_per_album[has_features].min())
X_knn = X_final[:, col_nnz >= safe_threshold]
```

This guarantees no album loses all its signal.

| Model | Features before prune | Features after prune | Albums indexed |
|-------|-----------------------|----------------------|----------------|
| v1 | 5,653 | 5,653 | 1,070,021 |
| v2 | 7,679 | 7,679 | 1,758,005 |
| v3 | 15,250 | 15,247 | 1,758,047 |

With the full-universe matrices, the safe threshold lands low (10 for v1, 1 for v2/v3), so little or nothing is pruned — the dense country and track-stats blocks keep almost every column above threshold.
