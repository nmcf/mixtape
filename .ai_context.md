# AI Context — mixtape

Internal reference for Claude Code sessions. Updated as the project evolves.

## What this project is

Album recommendation engine trained on the MusicBrainz open music database. A user enters an artist name, selects an album, and receives 10 similar album recommendations via a KNN model. Three model versions exist and can be compared side-by-side in the app.

## Tech stack

- **Data store:** MusicBrainz PostgreSQL (source) → Parquet files (working copy) → DuckDB (query layer for feature extraction)
- **ML:** scikit-learn `NearestNeighbors` with cosine distance, sparse scipy matrices
- **App:** Streamlit
- **Environment:** Python 3.11, virtualenv in `env/`

## Album universe

All matrices are built at the full album universe of **1,758,488** release groups (the
`valid_albums` scope — studio + official live + single-artist best-of). This replaced the
earlier 2,241,402 "type=1 only" universe that included live bootlegs, remixes and comps.

## Model versions

Numbers below are after the album-scope rebuild (universe = 1,758,488).

| Version | Feature blocks | Tag columns | Features (post-prune) | Albums indexed | Notebook |
|---------|---------------|-------------|----------------------|----------------|----------|
| v1 | tags · labels · types · ratings | 2,684 | 5,653 | 1,070,021 | 04-knn-training.ipynb |
| v2 | v1 + country · track stats | 2,684 | 7,679 | 1,758,005 | 11-knn-v2-training.ipynb |
| v3 | genre tags · record_label · ratings · country · track stats | 10,255 | 15,247 | 1,758,047 | 12-knn-v3-training.ipynb |

The current app, **`app_v3_weighted.py`**, uses the v3 feature blocks but does **not** load a
trained model — it reads the five raw feature matrices and computes weighted cosine directly
(see below), so the runtime knobs can reweight features. The trained models (v1/v2/v3) are still
produced by their notebooks but are gitignored.

Note: v1/v2 use the separate `album_labels_matrix` (2,958 cols) + `album_types_matrix` (10 cols);
v3 uses the combined `album_record_label_matrix` (2,968 cols). v2/v3 index ~1.76M albums vs v1's
1.07M (v1's tag-only feature set leaves more albums with no signal).

## Weighted app (Option B) — `app_v3_weighted.py`

Exposes the five v3 feature blocks as sidebar **knobs** (a custom HTML/SVG component). Loads the
raw (unweighted) matrices and precomputes per-block per-album sum-of-squares once at startup, then
per query computes: `numerator = Σ wᵦ²·(Xᵦ·qᵦ)`, album norms `= sqrt(Σ wᵦ²·ssqᵦ)`. No full-matrix
rebuild or renormalisation per query (~60–180 ms over the index). The album dropdown is filtered to
albums that have signal under the *current* weights, so it never offers an unservable album.

**Knob component** (`3-app/knob_component/index.html`): a guitar-amp-style rotary knob panel,
0–11 per knob, mapped to block weight via `dial_to_weight(d) = d/11·2.0` (0 → off, 11 → 2.0 max).
Click a tick around the ring to set a value. Defaults (dial units): Country = 2, others = 6
(mirrors the v3 training weights, country downweighted). Served over a tiny background
`HTTPServer` thread on port 8502 (Streamlit's built-in component file server failed in this
setup); registered via `declare_component(url=...)`. Messages to Streamlit need
`isStreamlitMessage: true`; after a click the component ignores inbound `render` events for 600 ms
to avoid a stale render reverting the value. `BLOCK_LABELS` carries `<br>` for two-line knob
labels — strip it (`.replace('<br>',' ')`) anywhere the label is shown outside the component (e.g.
the EQ caption). A "Reset Defaults" button restores dial defaults via an `on_click` callback.

**Two album-type filters** (sidebar `select_slider`s below the knobs), each an exact MusicBrainz
secondary-type lookup via `filter_by_flag()` / `load_flag_ids()`:
- **Live Albums** — Live / Both / Studio (secondary type Live=6, `mb_album_live_flag.parquet`)
- **Greatest Hits** — Collections / Both / Albums (secondary type Compilation=1,
  `mb_album_compilation_flag.parquet`)

Both default to Both and chain on both the artist-album dropdown and the recommendation results.
Replaced an earlier album-name keyword heuristic that mis-classified titles with no "live"
keyword (e.g. "Set List", date-format concert titles). See [[reference-mb-release-types]].

UI copy: title "Mixtape — Dial in Your Sound"; sidebar header "Tune your sound" / caption "Set the
balance to find your sound"; flow Set the Tone → Pick the Artist → Pick a Starting Album →
Checkout these albums; results caption "EQ — …".

Recommendations skip Various-Artists releases (null `artist_name`, ~1.5% of the index — VA
samplers that passed the import filter via the studio branch), since a release with no single
artist isn't actionable. Seeds are unaffected (dropdown is built from a selected real artist).

## Key design decisions

- **Album scope = `valid_albums`** (defined in `1-EDA/01-postgres-to-parquet.ipynb`): primary type = Album, must have an Official release (drops bootlegs), and is either studio (no secondary types), live (secondary type Live), or single-artist best-of (Compilation, non-VA). Other secondary types (Soundtrack, Remix, DJ-mix, Demo, …) and VA compilations excluded. Replaced the old "type=1 only" filter, which let in live bootlegs, remix collections and comps (e.g. U2 had 1,004 "albums" → 45 after the fix).
- **Bayesian weighted rating:** `score = (R × v) / (v + C)` with C=5. Collapses to 0 for unrated items.
- **Column pruning:** columns below `safe_threshold` nnz are dropped so no album with features loses all signal.
- **Same-artist exclusion:** recommendations filter out other albums by the same primary artist.
- **Album dropdown filtered** to albums present in any model's index.
- **Genre matrix blending:** artist tags only added for albums with < 5 direct tags (w=0.5, 92.2% of albums qualify); label tags always added (w=0.3); album tags always at w=1.0. Rows L1-normalised after combining.
- **Country downweighted to 0.2** — at w=1.0 it dominated cosine similarity due to density vs sparse tag columns.
- **Label weighting (fixed):** `album_label` parquet has one row per (album, label, tag) triple. Original weighting by `tag_count` underweighted boutique labels with few tags. Fixed to dedup (album, label) pairs and weight equally (1 / labels-per-album); the dedup slightly increases the label column count. (Current labels matrix: 2,958 cols at the post-rebuild universe.)
- **`album_record_label_matrix`** (v3) combines label identity + label type — both derived from `album_label`, encoding the same fact from two angles. v1/v2 keep them separate.
- **`album_types_matrix` is label types**, not release types — a side-product of the label feature build. Naming is misleading. It can NOT be used to detect live/compilation albums; the app's filters use the dedicated flag parquets instead (release-group secondary types from Postgres). See [[reference-mb-release-types]].
- **App album filters use exact MB secondary types, not name heuristics.** Live = secondary type 6, Compilation = 1. Flags pre-exported to single-column parquets and read into sets; an earlier album-name regex mis-classified titles like "Set List" and date-format concert names.
- **Label tags live only in the genre matrix.** The `tag_id` column in `album_label` feeds `album_genre_matrix` exclusively; it must NOT be used to weight the labels/record_label matrix (that was the bug above).
- **`artist_tags_matrix.npz`** exists but is not used directly in any model — artist tags are blended into `album_genre_matrix` instead.
- **Full-universe matrices:** all feature matrices are built and saved at the full album universe (currently 1,758,488) so block row dimensions always align for hstack. Mixing universes between blocks causes hstack dimension errors.
