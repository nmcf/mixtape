# AI Context — mixtape

Internal reference for Claude Code sessions. Updated as the project evolves.

## What this project is

Album recommendation engine trained on the MusicBrainz open music database. A user enters an artist name, selects an album, and receives 10 similar album recommendations via a KNN model. Three model versions exist and can be compared side-by-side in the app.

## Tech stack

- **Data store:** MusicBrainz PostgreSQL (source) → Parquet files (working copy) → DuckDB (query layer for feature extraction)
- **ML:** scikit-learn `NearestNeighbors` with cosine distance, sparse scipy matrices
- **App:** Streamlit (+ `streamlit-searchbox` for the artist typeahead; custom HTML/SVG components for knobs & faders)
- **Environment:** Python 3.11, virtualenv in `env/`

## Album universe

All matrices are built at the full album universe of **1,758,488** release groups (the
`valid_albums` scope — studio + official live + single-artist best-of). This replaced the
earlier 2,241,402 "type=1 only" universe that included live bootlegs, remixes and comps.

v3 uses the combined `album_record_label_matrix` (2,968 cols). v2/v3 index ~1.76M albums vs v1's
1.07M (v1's tag-only feature set leaves more albums with no signal).

## App — modular `5-app/` (entry point `app.py`)

Five modules: **`config.py`** (constants, presets, `BLOCK_FILES`, weight↔dial helpers), **`engine.py`**
(cached data loading, weighted cosine, auto-tune, explore search, artist index), **`controls.py`**
(sidebar widgets), **`style.py`** (themes/CSS), **`app.py`** (layout + two tabs). Full reference:
`docs/05-app.md`.

Loads the raw (unweighted) matrices and precomputes per-block per-album sum-of-squares once at
startup, then per query computes: `numerator = Σ wᵦ²·(Xᵦ·qᵦ)`, album norms `= sqrt(Σ wᵦ²·ssqᵦ)`.
No full-matrix rebuild or renormalisation per query (~60–180 ms over the index). The album dropdown
is filtered to albums with signal under the *current* weights, so it never offers an unservable album.

**Float weights (not discrete levels).** Weights are exact floats in [0.0, 2.0], stored in session
state as `wgt_{block}`. The 0–11 dial is a **display-only** rounding: `dial_to_weight(d)=round(d/11·2,4)`
and `weight_to_dial(w)=round(w/2·11)` (kept in `dial_{block}`). Presets store precise floats; scoring
always uses the float, the knob just snaps to the nearest integer tick. This replaced an earlier
teammate design that used coarse Off/Low/Medium/High levels.

**Blocks & knobs.** `BLOCK_FILES` loads genre, record_label, ratings, country, track_stats, era
(`album_temporal_matrix.npz`, 11 cols) and — if the file exists — popularity
(`album_lastfm_popularity_matrix.npz`). `KNOB_BLOCKS` excludes ratings: **ratings has no knob, its
weight auto-syncs to the Popularity dial** (both engagement signals; fixed fallback if popularity
absent). `DEFAULT_WEIGHTS`: genre/record_label/track_stats 1.09, era/popularity 0.73, country 0.36.
`BLOCK_LABELS` carries `<br>` for two-line knob captions — strip it (`.replace('<br>',' ')`) anywhere
the label is shown outside the component (e.g. the MIX caption under results).

**Presets & Auto-Tune.** Five presets (`PRESETS` in config) apply float weights via `_apply_weights()`.
Auto-Tune (`engine.auto_tune_profile` + `smart_auto_tune`) profiles per-block signal strength on the
seed album, combines with the user's current weights, and returns new **float** weights (applied the
same way as a preset).

**Custom sidebar widgets** (`knob_component/index.html`, `fader_component/index.html`) are served over
a background `HTTPServer` thread, registered via `declare_component(url=...)`; all postMessages carry
`isStreamlitMessage: true`. The knob panel re-seeds from persisted state on remount and ignores inbound
renders except when its `reset_nonce` (`knob_nonce`) is bumped (preset/reset/auto-tune). Faders are the
two **content filters**.

**Two content filters** (vertical faders) via release-group secondary type
(`data/raw/mb_album_secondary_type.parquet`, loaded by `engine.load_secondary_types`):
- **Live Albums** — STUDIO / BOTH / LIVE (secondary type Live=6)
- **Greatest Hits** — ALBUMS / BOTH / HITS (secondary type Compilation=1)

Default to STUDIO / ALBUMS. Exact MB lookup, not a name heuristic. See [[reference-mb-release-types]].
The faders apply to **all three album surfaces**: the album picker dropdown
(`passes_content_filters()` in `app.py`), Find Similar results (`engine.recommend`), and Explore
results (`engine.explore_search`). The active filter state is echoed in the results caption
(`FILTERS › STUDIO · ALBUMS`); if the secondary-type parquet is missing, a sidebar warning shows
and the caption reads `FILTERS › OFF` (filters silently no-op otherwise).

**Two tabs.** *Find Similar* (artist → album → weighted-cosine recs, with a "why" per-block breakdown)
and *Explore* (genre-tag + country + decade discovery → seed a result into Find Similar). Explore needs
`data/raw/mb_tag.parquet` (tag vocabulary) — degrades to a hint if absent.

**Artist search** is a live typeahead (`streamlit-searchbox`'s `st_searchbox`): matching artists from
the lookup appear/refine per keystroke (prefix matches first, capped at 50). `engine.artist_index()`
caches the ~566k unique names with a precomputed lowercased column; `engine.make_artist_search()`
builds the callback (uses `re.escape` so band names with regex metachars like `+44`, `!!!` don't error).
Selecting a suggestion goes straight to the album picker.

Recommendations skip Various-Artists releases (null `artist_name`, ~1.5% of the index). Seeds are
unaffected (dropdown is built from a selected real artist).

## Key design decisions

- **Album scope = `valid_albums`** (defined in `1-data/01-postgres-to-parquet.ipynb`): primary type = Album, must have an Official release (drops bootlegs), and is either studio (no secondary types), live (secondary type Live), or single-artist best-of (Compilation, non-VA). Other secondary types (Soundtrack, Remix, DJ-mix, Demo, …) and VA compilations excluded. Replaced the old "type=1 only" filter, which let in live bootlegs, remix collections and comps (e.g. U2 had 1,004 "albums" → 45 after the fix).
- **Bayesian weighted rating:** `score = (R × v) / (v + C)` with C=5. Collapses to 0 for unrated items.
- **Column pruning:** columns below `safe_threshold` nnz are dropped so no album with features loses all signal.
- **Same-artist exclusion:** recommendations filter out other albums by the same primary artist.
- **Album dropdown filtered** to albums present in any model's index.
- **Genre matrix blending (3-tier):** album tags always at w=1.0; **artist tags added for ALL albums** at w=0.5 (the old `< 5 direct tags` threshold was dropped — universal artist tags add *richness* to already-covered albums, not coverage); label tags at w=0.3 in two modes — **reinforcement** (masked to only boost tags the album/artist already has — ~87% of raw label-tag entries are masked out as genre-noise) and **rescue** (allowlist labels only, only for albums with zero album+artist signal). Rows L1-normalised after combining. Genre coverage: **1,210,648 albums (68.8%)** — near the tag-signal ceiling.
- **Label genre-coherence allowlist:** a label joins the allowlist if ≥60% of its albums share at least one tag with the label (per-album overlap rate). Label size and `label_type` are poor proxies for genre coherence (it is bimodal at every size), so the overlap rate is used directly. Only allowlist labels may *introduce* new genre signal for zero-signal albums. Computed at build time in `feature-genre.ipynb`.
- **Coverage vs richness:** coverage = does an album have any genre signal (binary); richness = how many distinct genre tags an already-covered album carries. Universal artist tags give **+0 coverage** (provably — the only newly-blended albums are ≥5-direct-tag albums that were already covered) but increase richness, which sharpens cosine similarity. See `2-eda/05-EDA-tags-labels.ipynb`.
- **Country downweighted to 0.2** — at w=1.0 it dominated cosine similarity due to density vs sparse tag columns.
- **Label weighting (fixed):** `album_label` parquet has one row per (album, label, tag) triple. Original weighting by `tag_count` underweighted boutique labels with few tags. Fixed to dedup (album, label) pairs and weight equally (1 / labels-per-album); the dedup slightly increases the label column count. (Current labels matrix: 2,958 cols at the post-rebuild universe.)
- **`album_record_label_matrix`** (v3) combines label identity + label type — both derived from `album_label`, encoding the same fact from two angles. v1/v2 keep them separate.
- **`album_types_matrix` is label types**, not release types — a side-product of the label feature build. Naming is misleading. It can NOT be used to detect live/compilation albums; the app's filters use the dedicated flag parquets instead (release-group secondary types from Postgres). See [[reference-mb-release-types]].
- **App album filters use exact MB secondary types, not name heuristics.** Live = secondary type 6, Compilation = 1. Flags pre-exported to single-column parquets and read into sets; an earlier album-name regex mis-classified titles like "Set List" and date-format concert names.
- **Label tags live only in the genre matrix.** The `tag_id` column in `album_label` feeds `album_genre_matrix` exclusively; it must NOT be used to weight the labels/record_label matrix (that was the bug above).
- **`artist_tags_matrix.npz`** no longer exists as a committed file — artist tags are blended into `album_genre_matrix` during the feature build. The EDA notebook (`05-EDA-tags-labels.ipynb`) rebuilds artist-tag statistics inline from `mb_artist_tag.parquet`.
- **Full-universe matrices:** all feature matrices are built and saved at the full album universe (currently 1,758,488) so block row dimensions always align for hstack. Mixing universes between blocks causes hstack dimension errors.
